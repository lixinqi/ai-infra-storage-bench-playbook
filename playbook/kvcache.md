# KVCache 存储评估

推理侧的存储评估。评估对象是 kvcache 的分配、写入、读取、复用、驱逐与跨节点搬运。本篇只写这条路径的特殊之处，旁路与保真的总则见 [`methodology.md`](methodology.md)。

## 1. 目标

在真实存储与传输路径上，测出推理服务产生的 kvcache IO 行为，覆盖多种模型与多种推理框架，并把结论外推到十万卡规模的推理集群。

要回答的问题：

1. 单个请求在 prefill 与 decode 阶段各产生多少 KV 读写，请求大小分布如何。
2. 前缀复用（prefix cache）命中时，读放大的倍数与命中率的关系。
3. 驱逐与 offload 策略触发的写入有多少，什么时候触发。
4. 跨节点 KV 传输的流量、对端分布与时序，随集群规模怎么变。

## 2. 评估对象

| 路径 | 说明 | 是否保真 |
|---|---|---|
| KV 分配与释放 | 块分配器、页表、碎片整理 | 是 |
| KV 写入 | prefill 阶段按 token 写 K/V，decode 阶段逐 token 追加 | 是 |
| KV 读取 | attention 读取历史 KV | 是 |
| 前缀复用 | 命中、部分命中、未命中三种情况的读写 | 是 |
| 驱逐与 offload | 显存不足时的换出、丢弃、分层缓存 | 是 |
| 跨节点 KV 传输 | 预填充与解码分离、分布式前缀缓存 | 是 |
| prefill / decode 计算 | attention 计算、FFN、采样 | 否，旁路 |

kvcache 的 IO 特征与训练侧完全不同，配方里不能复用训练侧的阈值：

- 请求小：decode 阶段每个 token 的一次 KV 写只有"层数 × KV 头数 × head_dim × dtype"字节，常见在几百字节到几 KB。
- 突发性强：请求到达决定何时读写，时间序列由调度器决定，不由计算决定。
- 读写混合：同一个块会被反复读、追加写、最终驱逐，生命周期短。
- 依赖框架内部状态：块表、前缀树、缓存层级全部在框架内部，观测点必须贴着框架的接口放。

## 3. 旁路 prefill / decode 计算

### 3.1 做法

1. 模型用 `meta device` 构建，权重只保留 dtype 与逻辑尺寸。
2. attention 计算替换为占位实现：不计算 QK^T 与 softmax，但按真实的块编号与偏移访问 KV 块。**块表与偏移必须真实传递**，这是 IO 的真来源。
3. FFN、norm、采样全部替换为占位实现。
4. 调度器、块管理器、前缀缓存、传输层一律不改。
5. 输入请求序列由负载配置生成：到达间隔、输入长度、输出长度、并发数。

### 3.2 关键约束

- **不能改框架核心代码**。适配层放在框架外部，通过框架已有的插件点（自定义 attention backend、自定义缓存后端、连接器接口）接入；没有插件点时，维护一份最小 patch 清单，记录 patch 的版本适用范围。
- 旁路后的 attention 必须真的去读 KV 块，否则读路径的 IO 会消失，测出来的读放大是错的。
- 采样与停止条件必须保留，否则请求长度分布会变，进而改变 KV 的写入总量。

## 4. 框架适配层

需要适配的框架：vllm、sglang、deepinfer。适配层对外暴露统一接口，对内分别实现：

| 接口 | 语义 | vllm | sglang | deepinfer |
|---|---|---|---|---|
| `alloc_block` / `free_block` | 块的分配与释放 | 以当期版本的块管理器接口为准 | 以当期版本的 radix cache 接口为准 | 以该框架当期接口为准 |
| `read_kv` / `write_kv` | 按块偏移读写 | 同上 | 同上 | 同上 |
| `transfer_kv` | 跨节点搬运 | 以 KV 连接器接口为准 | 以分层缓存接口为准 | 以该框架当期接口为准 |
| `on_evict` | 驱逐事件 | 以块管理器回调为准 | 以 radix cache 回调为准 | 以该框架当期回调为准 |
| `scheduler_events` | 请求的排队、开始、结束 | 以调度器事件为准 | 同 | 同 |

表格里的"以当期版本为准"不是含糊，而是明确要求：**适配层必须对照具体版本的接口实现，版本号写进配方。** 框架接口变化频繁，任何写死的接口描述都会过期。

适配层的验收：

1. 同一份负载配置下，三个框架产出的事件序列（分配、写、读、驱逐、传输）在语义上一致，数量级在合理范围内。
2. 每个框架的适配都有一份最小验证用例，能在 CI 里 5 分钟内跑完。
3. 框架升级时，适配层失败要显式报错，不允许静默降级到"无 IO"。

## 5. 流程与阶段门

| 步骤 | 内容 | 通过条件（门） |
|---|---|---|
| 1 | 选模型与框架，跑通一次不旁路的推理 | G0：能跑 |
| 2 | 接入 meta device 与占位 attention，保留块管理与传输 | G1：旁路可跑，保真边界表填完 |
| 3 | 小集群小参数规模，与真实小规模运行对比 IO pattern | G2：选定度量项在容差内 |
| 4 | 换模型：从模型代码库取样，覆盖不同层数、KV 头数、注意力变体 | G3-a：多模型适配通过 |
| 5 | 换框架：三个框架各跑通同一套负载 | G3-b：多框架适配通过 |
| 6 | 放大参数规模 | G3-c：不变量保持 |
| 7 | 先放大到万卡（S4），再外推到十万卡（S5） | G3-d：不变量保持 |
| 8 | 登记结论与回链 | G4：回链三要素齐全 |

第 4、5 两步是矩阵的两个轴，可以并行推进，但都不允许在第 3 步通过之前开始。

## 6. 小规模对齐

对齐基准是不旁路的同规模真实推理。除 `methodology.md` 的通用度量项外，kvcache 额外对齐：

| 度量项 | 定义 | 说明 |
|---|---|---|
| 每 token KV 写入字节 | 写入总字节 / 生成的 token 数 | 应与模型结构严格对应，可直接算出来核对 |
| 前缀命中率 | 命中块数 / 请求块数 | 旁路不应改变命中率 |
| 读放大倍数 | KV 读取字节 / 写入字节 | 由 attention 访问历史长度决定 |
| 驱逐次数与时点 | 单位时间驱逐的块数 | 由显存容量与调度策略决定 |

第一条最有用：每 token 的 KV 写入字节可以由模型配置直接算出，把算出来的值与测出来的值对比，能最快发现旁路实现漏掉了写路径。

## 7. Scaling

| 维度 | 不变量（应保持） | 变量（预期变化） |
|---|---|---|
| 模型规模 ↑ | 每 token 每层每 KV 头的字节数 | 单请求 KV 总量、单块大小 |
| 并发请求数 ↑ | 单请求的请求大小分布 | 总带宽、驱逐频率 |
| 序列长度 ↑ | 单次读的请求大小 | 读放大倍数、块复用距离 |
| 集群规模 ↑ | 单节点内的读写特征 | 跨节点流量、对端分布、带宽争用 |
| 缓存层级 ↑ | 单层的读写请求特征 | 层间搬运量与命中率 |

## 8. 验收

| 指标 | 口径 | 说明 |
|---|---|---|
| 多模型适配覆盖率 | 已适配模型数 / 目标模型数，按注意力变体分桶 | 每桶至少 5 个 |
| 多框架适配覆盖率 | 三个框架均通过同一套负载 | 缺一不可 |
| prefill / decode 对齐度 | 两个阶段分别计算 | 阶段不同，容差不同 |
| 每 token KV 字节核对 | 计算值与观测值的相对误差 | ≤ 1% |
| scaling 一致性 | 见 `metrics/scaling-consistency.md` | 每一级都要算 |

## 9. 开放问题

- 跨节点 KV 传输在框架间差异最大，没有统一的语义抽象，适配层容易出现抽象泄漏。
- 前缀缓存的命中率高度依赖负载，负载配置怎么定为"有代表性"，目前只靠经验。
- 驱逐策略的触发依赖显存容量，小规模对齐时显存压力不足，驱逐路径覆盖不到。
- prefill 与 decode 分离部署时，传输的时序由两个服务协同决定，单机旁路难以复现。
- 三个框架的版本节奏不同，适配层的回归周期如何与框架发布节奏对齐。
