# Scaling：不变量、逐级验证与外推

三类评估集共用这套方法。它回答一个问题：**在小规模上测出来的结论，凭什么能用到十万卡。**

评估集的上限按十万卡设计。

## 1. 为什么要单独成文

scaling 不是"把参数调大再跑一次"。放大过程中至少有三类东西同时在变：

- 数据本身变：分片数、每片大小、每 rank 的请求量。
- 系统变：聚合带宽、元数据操作数、排队与拥塞、缓存命中率。
- 策略变：并行切分方式、写入并发度、调度策略。

如果不把"哪些应该不变、哪些一定会变"写清楚，放大之后测到的差异无法区分是"存储扛不住"还是"配置变了"。

## 2. Scaling 维度

| 维度 | 具体量 | 影响 |
|---|---|---|
| 模型规模 | 参数量、层数、隐藏维度、KV 头数 | 单请求数据量、单分片大小 |
| 集群规模 | 节点数、卡数、每节点卡数 | 并发度、聚合带宽、元数据请求数 |
| 并行策略 | DP / TP / PP / EP 的组合与度数 | 分片方式、通信分组、每 rank 负载 |
| 负载 | 并发请求数、序列长度、到达间隔、请求分布 | 读写比、突发模式、缓存命中率 |
| 存储后端 | 文件系统、对象存储、分层缓存 | 请求大小上限、元数据成本、一致性代价 |

一次评估只沿一个维度放大，其余维度固定并记录。同时放大两个维度得到的结论无法归因。

## 3. 怎么定 scaling 不变量

不变量不是凭经验直接指的，按流程定：

1. **列出候选**：从 `methodology.md` 的度量项里，挑出与本次评估目标相关的项。
2. **判断它会不会随目标维度变**：写出理由。会变的，是变量，不是不变量。
3. **判断它能不能被测量**：测不到的不能当不变量。
4. **判断它变了是否意味着结论失效**：如果变了也不影响结论，它只是参考项。
5. **定容差**：不变量允许的波动范围，必须可计算。

每条不变量写进配方的 `metrics.yaml`，包含：名称、定义、计算方式、容差、判定规则。

不变量选得太多，验证成本高且互相矛盾；选得太少，外推没有依据。经验范围是每条评估集 3–6 条。

示例（checkpoint 评估集）：

| 不变量 | 定义 | 容差 | 为什么稳定 |
|---|---|---|---|
| 每 rank 请求大小分布 | 该 rank 单次 checkpoint 内所有写请求的字节数直方图 | L1 距离 ≤ 0.1 | 由分片策略决定，参数规模放大时每片大小按比例放大，直方图的相对分布稳定 |
| 每参数字节数 | 一次 checkpoint 写入总字节 / 参数量 | 相对误差 ≤ 2% | 由精度、优化器状态与分片冗余决定，与规模无关 |
| 单 rank 写入并发度 | 单 rank 同时在途的写请求数 | 中位数相对误差 ≤ 15% | 由框架的写入并发配置决定 |

## 4. 逐级验证阶梯

不允许从最小规模直接跳到十万卡。阶梯至少四级，当前按六级执行：

| 级 | 规模 | 目的 | 通过条件 |
|---|---|---|---|
| S0 | 单机，最小参数规模 | 对齐基准 | 度量项在容差内 |
| S1 | 单机多卡或双机 | 引入并行切分与多 rank 并发 | 不变量保持 |
| S2 | 数十至百卡 | 引入网络与共享存储的争用 | 不变量保持，偏差有归因 |
| S3 | 千卡 | 引入调度与故障恢复 | 不变量保持，偏差有归因 |
| S4 | 万卡 | 实测上限 | 不变量保持，偏差有归因 |
| S5 | 十万卡 | 外推目标 | 不变量保持，外推结论登记 |

每一级的采样点数量不必相同，但每一级都必须拿到完整度量，不允许"只测了带宽"。

阶梯的级别不是固定的：如果存储后端在 S2 就已经饱和，S3 到 S5 的重点就从"测请求特征"变成"测排队与尾延迟"。这要在配方里预先写明，不要跑完才发现测错了东西。

## 5. 外推规则

### 5.1 线性的前提

聚合带宽 = 单 rank 带宽 × rank 数，这个式子只在**存储侧未饱和**时成立。饱和之后，增加 rank 不会增加聚合带宽，只会增加排队与尾延迟。

判定是否饱和的方法：看单 rank 带宽随 rank 数增长的曲线。曲线开始走平的那一点就是饱和点，之后一律用排队模型描述，不用线性外推。

### 5.2 元数据与数据分开外推

- 数据字节数随参数量线性增长。
- 元数据操作数随**分片数与文件数**增长，与总字节无关。分片数随集群规模增长时，元数据可能比数据先到上限。

两条曲线要分开算，分开报告。合成一条会掩盖真正的瓶颈。

### 5.3 时序与重叠

- 同步写入：写入期间训练停顿，IO 是独占的。
- 异步写入：写入与计算重叠，实际带宽需求是写入量除以重叠窗口长度。计算被旁路后窗口变短，测量值会偏高，必须按真实计算时长折算。

折算规则写进配方：用真实运行测得的计算时长中位数，把旁路运行的写入时间轴拉伸到真实长度。

### 5.4 尾延迟

大规模评估关心 P99 与 P999，不关心平均值。尾延迟随规模超线性增长（排队、重传、元数据热点），不能按平均值外推。

## 6. 非线性来源清单

放大过程中出现超线性变化，先排查这些来源，再下结论：

| 来源 | 表现 | 排查方法 |
|---|---|---|
| 存储侧饱和 | 带宽走平、尾延迟陡增 | 单 rank 带宽随规模曲线 |
| 元数据热点 | 小请求耗时随规模急剧上升 | 按操作类型拆分延迟 |
| 网络拥塞 | 跨节点流量抖动、重传增加 | 网络计数器与重传率 |
| 缓存命中率下降 | 实际打到远端的请求变多 | 分层统计命中率 |
| 负载不均衡 | 部分 rank 长时间空闲、部分饱和 | 每 rank 的请求量分布 |
| 调度抖动 | 长尾请求集中在少数节点 | 按节点拆分尾延迟 |
| 故障恢复 | 重启后短时间 IO 放大 | 恢复窗口内的请求序列 |

## 7. 报告要求

每一级 scaling 的报告必须包含：

1. 该级的完整配置（模型、并行、拓扑、存储后端、负载）。
2. 声明的不变量表，以及实测值与容差的对比。
3. 变量表，以及实测值随规模的变化曲线。
4. 偏差归因：哪些偏差来自系统，哪些来自配置变化。
5. 下一级的预测值与预测依据。

报告本身放对象存储，仓库里只写回链。

## 8. 开放问题

- 中间规模的采样点怎么选：目前按"每级不超过上一级的 4 倍"经验取值，没有理论依据；千卡到万卡这一级跨了约 10 倍，是已知的例外。
- 十万卡规模的真实运行成本过高，是否允许用部分模拟加部分真实的方式替代，替代的可信度如何界定。
- 不同存储后端的外推规则不通用，是否需要按后端各写一份。
- 并行策略在放大过程中往往同时变化，"只沿一个维度放大"的要求在实际中难以满足，需要明确的例外规则。
