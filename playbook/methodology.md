# 核心方法论：旁路计算，保真 IO

本文是整套方法的唯一出处。旁路、保真等级、保真边界表、IO pattern 度量项、对齐判定、阶段门只在这里定义一次；三类评估集的配方引用本文的章节，只写各自的差异。

本文解决"评估集怎么建、怎么判它可信"。存储在一个样本上的表现（SLI）怎么测、重保子集怎么判（SLO）、两个存储版本怎么比，见 [`storage-performance.md`](storage-performance.md)，两篇的分工不要混。

## 0. 这篇先写

先写本文，再写配方。理由不是篇幅，是定义只能有一份：三份配方各自定义一遍"保真"，三个月后就会出现三种保真。

| 配方 | 引用本文的节 | 只写差异的部分 |
|---|---|---|
| `recipes/model-code-collection` | 第 2、3、4 节 | 语料不变量、可跑性验证 |
| `recipes/checkpoint-dataset` | 第 2–9 节 | meta device 旁路、并行配置、dataset 布局 |
| `recipes/kvcache` | 第 2–9 节 | 占位 attention、框架适配、prefill/decode 拆分 |

引用规则：

1. **概念只定义一次。** 配方里出现与本文冲突的表述，以本文为准，并修正配方。
2. **新规则先写进本文，再改配方。** 倒过来会让三份配方各自长出一套说法。
3. **改本文等于改三类评估集的共同定义。** 评审要求与改指标口径相同：说明影响哪些配方、哪些历史结论失效，并在 `CHANGELOG.md` 记录。
4. **配方只写差异。** 共性的步骤、表格、判定规则引用本文的章节标题加路径，不复制。

## 1. 为什么可以旁路计算

存储与传输侧的评估对象是 IO。计算部分对 IO 的贡献只有三件事：什么时候发起、一次发起多少、以什么并发度发起。计算本身的数值正确性、算子实现、kernel 性能，都不进入评估结论。

因此：把计算换成不产生真实计算的实现，只要保证**发起 IO 的代码路径没有被替换**，得到的 IO 请求序列依然能代表真实运行。

这条推理有一个前提必须显式检查：旁路手段不能改变 IO 的发起时机与批量。例如用 meta device 后 forward 瞬间返回，原本被计算掩盖的 checkpoint 写入就会挤在一起，时序被压缩。这类偏差必须登记，不能默认不存在。

## 2. 一次评估的阶段门

每个配方都必须按这五道门推进，每道门有明确的产出：

| 门 | 名称 | 通过条件 | 产出 |
|---|---|---|---|
| G0 | 能跑 | 目标代码在不旁路的情况下能跑完一次前向或一次预填充 | 可运行的最小配置 |
| G1 | 旁路可跑 | 旁路实现后能跑完同样流程，且 IO 路径未被替换 | 保真边界表 |
| G2 | 小规模对齐 | 选定度量项在容差内 | 对齐报告的回链 |
| G3 | 逐级 scaling | 每一级的不变量都在容差内，偏差有归因 | scaling 报告的回链 |
| G4 | 结论登记 | 回链三要素齐全，覆盖率矩阵更新 | `recipe.yaml` 的 `latest_run` |

G1 到 G4 的判定记录写进 `recipe.yaml`，不写进文档正文。

## 3. 旁路手段与保真等级

四种手段，成本与保真度递增：

| 手段 | 做法 | 请求序列的保真等级 | 成本 | 适用 |
|---|---|---|---|---|
| meta device | 张量只保留 dtype 与逻辑尺寸，不分配显存/内存 | L2 | 极低 | 需要真实控制流的全部计算 |
| 模块 mock | 替换指定模块的 forward/step，返回预先约定的张量 | L2 | 低 | 只关心某几条 IO 路径，其余整段旁路 |
| CPU offload | 计算在 CPU 上用极小规模真实执行 | L2 | 中 | 需要真实 kernel 调用顺序，但不需要 GPU |
| 真实小规模 | 不做旁路，直接小规模真实运行 | L3 | 高 | 对齐基准，用于标定其它手段的偏差 |

这张表只给**请求序列**的保真等级，不给时序的。旁路计算后时序一定被压缩：原本散布在整个训练步里的写入会挤到末尾。时序按 [`scaling.md`](scaling.md) 的「时序与重叠」折算，必要时在旁路实现里注入与真实计算等长的延迟。请求序列与时序必须分开评估，不能用一个等级同时概括。

保真等级定义：

| 等级 | 含义 |
|---|---|
| L0 | 只保证调用到同一对外接口，内部实现已被替换（例如用自己的写入器替代框架的 checkpoint 实现） |
| L1 | 代码路径相同，但请求在本地被缓冲或合并，请求的大小与偏移已经改变 |
| L2 | 代码路径与请求序列相同，每条请求与真实运行一一对应 |
| L3 | 在 L2 之上，时序与并发也与真实运行一致，跨节点传输是真实的 |

L2 是大多数场景的默认目标：它保证"发了哪些请求"，不保证"什么时候发"。L3 只用于对齐基准，不用于批量运行（成本不允许）。

## 4. 保真边界表

每个配方必须填写。没有这张表的配方视为未完成。

字段：

| 字段 | 含义 | 填写要求 |
|---|---|---|
| `path` | 被登记的代码路径或模块 | 写到函数级，例如 `torch.distributed.checkpoint.save` |
| `bypassed` | 是否被旁路 | `yes` / `no` / `partial` |
| `method` | 旁路手段 | meta device / module mock / CPU offload / 真实小规模 |
| `fidelity` | 保真等级 | L0–L3 |
| `kept` | 保留了什么 | 必须具体，例如"每个 rank 的独立分片写入" |
| `known_bias` | 已知偏差 | 没有就写 `none`，不要留空 |

填写规则：

1. **IO 路径一律不允许写 L0。** 如果某条存储路径确实是 L0，说明评估对象已经被替换，该路径的结论无效。
2. `partial` 必须写清楚部分的范围边界，例如"写入路径真实，元数据提交被 mock"。
3. `known_bias` 要能回答"这个偏差会往哪个方向推高或压低测得的指标"。答不出来的偏差，说明还没理解它。

示例（checkpoint 写入路径）：

| path | bypassed | method | fidelity | kept | known_bias |
|---|---|---|---|---|---|
| forward / backward / optimizer.step | yes | meta device | — | 控制流、参数顺序、梯度的逻辑尺寸 | 计算耗时为 0，写入时序可能被压缩 |
| 分片策略（DP/TP/PP/EP 切分） | no | — | L2 | 分片数量、每片大小、rank 归属 | 无 |
| checkpoint 写入与元数据提交 | no | — | L2 | 真实的写入调用、真实的对象存储/文件系统 | 无 |
| 通信原语（all-gather / reduce-scatter） | partial | mock process group | L1 | 调用次数与数据量 | rank 间真实同步丢失，交织时序失真 |

## 5. IO pattern 的度量项

说"对齐 IO pattern"之前，必须先说清对齐哪几项。以下度量项是所有评估集共用的词汇表，配方从中挑选。

| 度量项 | 定义 | 采集方式 |
|---|---|---|
| 请求大小分布 | 每个 IO 请求字节数的直方图，按 4 KiB 起对数分桶 | 应用层 hook 或存储客户端日志 |
| 读写比 | 两个口径：按字节数、按请求数 | 同上 |
| 顺序性 | 相邻请求的逻辑偏移差与请求大小的比值；1 表示严格顺序 | 应用层 hook |
| 并发度 | 同时在途的请求数分布（中位数、P95、峰值） | 应用层 hook 或队列深度采样 |
| 队列深度 | 设备或客户端队列的排队请求数 | 系统层采样 |
| 时序 | 每秒请求数与每秒字节数的时间序列；突发窗口长度与峰值 | 系统层计数 |
| 热度 | 按数据块统计的访问次数分布：Top-K 占比、Gini 系数 | 应用层 hook（按偏移聚合） |
| 生命周期 | 同一数据块从首次写入到被读取或被驱逐的时长 | 应用层 hook |
| 跨节点流量 | 每个 rank 的出/入字节数、对端节点分布、通信与存储的时间重叠 | 网络计数器 + 应用层 hook |

每条评估集配方从中挑 3–6 项作为 scaling 不变量，其余作为参考项。挑得太多无法验证，挑得太少外推没有依据。

## 6. 采集

三层观测，至少要两层交叉核对：

| 层 | 位置 | 能拿到什么 | 局限 |
|---|---|---|---|
| 应用层 | 在数据加载器、写入器、block manager 外面包一层 | 请求的逻辑含义、偏移、大小、调用栈 | 看不到合并后的真实请求 |
| 系统层 | 块设备 trace、文件系统客户端统计、网络计数器 | 真实下发的请求、排队、重传 | 丢失逻辑归属，难以按 rank 拆分 |
| 存储侧 | 存储服务端的请求日志与指标 | 服务端视角的吞吐、尾延迟、元数据操作 | 采样率与聚合粒度受限 |

交叉核对规则：

- 应用层统计的总字节数与系统层统计的总字节数，偏差超过 1% 必须先解释，再使用任何 pattern 结论。
- 解释不清时，先怀疑观测本身：采样丢点、缓冲未刷、统计口径把元数据算进或漏出。
- 观测开销单独测量：开启与关闭观测各跑一次，若关键指标变化超过 3%，降低采样率或改用系统层。

## 7. 对齐

"对齐"是可判定的，定义如下：

> 在选定的度量项上，旁路运行与同等规模的真实运行，其统计量落在声明的容差内。

初始容差（标定前视为待验证）。**实际判定用配方 `metrics.yaml` 里的 `tolerance`，本表只是标定起点**：

| 度量项 | 对齐指标 | 初始容差 |
|---|---|---|
| 请求大小分布 | 分桶频率的 L1 距离 | ≤ 0.10 |
| 读写比 | 字节口径的相对误差 | ≤ 5% |
| 并发度 | 中位数相对误差、P95 相对误差 | 分别 ≤ 10%、≤ 20% |
| 时序 | 峰值窗口内的字节数相对误差 | ≤ 10% |
| 热度 | Top-K 占比的绝对差 | ≤ 0.05 |
| 顺序性 | 顺序请求占比的绝对差 | ≤ 0.05 |

容差需要按评估集分别标定：kvcache 的 decode 阶段请求小、突发强，容差应比 checkpoint 宽；checkpoint 写入的请求大小由分片策略决定，容差应更紧。标定结果写进配方的 `metrics.yaml`，并注明标定日期与所用基准。

对齐失败时按以下顺序归因，逐项排除：

1. 观测开销改变了 pattern（先关掉观测对比）。
2. 本地缓冲或合并改变了请求的边界（检查文件系统页缓存、写入缓冲、批量提交）。
3. 旁路改变了时序（计算耗时为 0，写入挤在一起；单卡串行跑 rank 导致并发降低）。
4. allocator 差异（meta device 不分配真实内存，allocator 行为、对齐、碎片都不同）。
5. 冷热缓存差异（首次运行与重复运行差别很大，必须固定预热策略）。
6. 通信 mock 丢失了 rank 间同步（并发度与交织时序失真）。

归因结论写进配方的 `README.md`，不要只留在聊天记录里。

## 8. Scaling

总则见 [`scaling.md`](scaling.md)。方法论文档只强调两点：

- 对齐通过之前，不允许进入 scaling。在对不齐的小规模上放大，只会把偏差放大。
- 每一级 scaling 都要重新验证不变量。跳级得到的结论没有依据。

## 9. 可复现

一次评估要能被别人重跑出同样的结论，需要固定：

| 项 | 固定方式 |
|---|---|
| 模型代码 | 记录仓库地址与 commit，不只记录 model id |
| 配置 | 记录完整配置文件与哈希 |
| 依赖 | 记录 lock 文件与镜像版本 |
| 拓扑 | 记录 rank 数、每节点卡数、网络拓扑、存储挂载方式 |
| 预热 | 记录预热方式与预热轮数 |
| 观测 | 记录观测开关、采样率、观测本身的开销 |
| 随机性 | 数据顺序、shuffle 种子、请求注入顺序全部固定 |

缺任何一项，结论都只能算"某次运行的观测"，不能算"评估结论"。

## 10. 失效模式

| 失效模式 | 现象 | 处置 |
|---|---|---|
| 观测开销污染 | 开观测后吞吐下降、请求变小 | 降采样，改用系统层，单独测量开销 |
| 缓冲合并 | 应用层看到 4 KiB 写，设备层看到 1 MiB 写 | 以系统层为准，应用层只用于逻辑归属 |
| 时序压缩 | 旁路后写入全部挤在最后 | 在旁路里注入等时延迟，或按真实时间轴采样 |
| 单卡串行 | 并发度远低于真实 | 用多进程、多流模拟并发，或明确登记为已知偏差 |
| 缓存差异 | 首轮与次轮差异大 | 固定预热，报告只取稳态窗口 |
| 通信 mock 失真 | rank 间不同步，交织时序消失 | 关键路径改用真实通信，或把该路径排除在结论之外 |

更多已知问题与开放问题见 [`pitfalls.md`](pitfalls.md)。
