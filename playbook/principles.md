# 定位与原则

## 一句话

本仓库是生成评估集的 playbook：一套配方、指标与流程，产出 AI Infra 存储与传输侧的评估集。它回答三个问题：**测什么、怎么测、测完怎么让下一版测得更多。**

## 为什么做一套持续维护的 benchmark

一次性的测跑能回答"当前实现有多快"，回答不了下面三个问题，而这三个问题正是需要一套持续维护的 benchmark 的原因：

1. **覆盖是否够**：真实模型代码产生的 IO 是长尾的。少数几个旗舰模型覆盖不到分片写入、小文件元数据、跨节点 KV 搬运这些会打垮存储的场景。
2. **结论是否可外推**：单机测出来的结论在十万卡上未必成立，因为聚合带宽、元数据放大、并行策略都在变。
3. **覆盖度是否在衰减**：新模型、新推理框架出现后，bench 若没有机制发现缺口并生成新版本，覆盖度会随时间下降。

评估集提供覆盖与外推依据；评估服务负责持续运行；扩展机制负责覆盖度不衰减——它由 playbook 执行，评估集本身不变。三者缺一，闭环就断。

## 三部分的关系

```text
          ┌──────────────────────────────────────────────┐
          │                                              │
          ▼                                              │
   当前版本的评估集（覆盖度矩阵）                                    │
          │                                              │
          ▼                                              │
   评估服务：跑用例 → 产出 IO pattern 与结论                │
          │                                              │
          ▼                                              │
   缺口分析：新架构 / 新框架 / 新并行策略 / 未覆盖的 IO 特征   │
          │                                              │
          ▼                                              │
   playbook 生成新版本：新用例、新配方、新适配层              │
          │                                              │
          ▼                                              │
   回归：旧用例结论是否仍然成立 ────────────────────────────┘
```

闭环里人的位置是明确的：**自动发现缺口、自动生成候选用例、自动回归；人审核口径变更、阈值调整、以及任何会让历史结论不可比的改动。**

## 三类评估集的关系

```text
模型代码收集库（原料）
   ├── 推理模型代码，1000+，尽量配对训练代码
   ├── 结构去重后的多样性覆盖
   └── mock process group 可跑性验证
          │
          ├── checkpoint / dataset 存储评估集（训练侧）
          └── kvcache 存储评估集（推理侧）
```

模型代码收集是**前置原料库**，另外两类评估集从库里取样构建。这条依赖要在配方里显式声明：checkpoint/dataset 与 kvcache 的 `recipe.yaml` 都必须写 `depends_on: recipes/model-code-collection`。

## 本仓库管什么

- 模型代码的收集、去重、可跑性验证方法。
- 训练侧 checkpoint 与 dataset 的存储评估方法。
- 推理侧 kvcache 的存储评估方法。
- 旁路计算、保留 IO 的通用方法，以及保真程度的登记方式。
- 小规模对齐与 scaling 外推的方法。
- 评估服务的接口、调度、结果回链规范。
- playbook 扩展评估集的触发条件、缺口分析、审核边界。
- 指标口径、阈值、验收标准与校验脚本。

## 本仓库不管什么

| 不管 | 原因 |
|---|---|
| 模型训练与推理的性能调优 | 那是被评估对象，不是评估设施 |
| 计算 kernel 优化 | 与存储传输侧的 IO 无关 |
| 存储硬件选型 | 硬件选型的输入来自评估结论，选型决策不在这里做 |
| 生产集群运维 | 评估集群与生产集群是两套环境 |
| 一次性 benchmark 报告的归档 | 报告是运行产物，只回链，不入库 |
| 原始数据集、模型权重、checkpoint | 体积与权限都不适合放进仓库 |

## 三条硬原则

### 1. 计算可以假，IO 必须真

评估的目的是存储传输侧。计算部分（forward、backward、optimizer、prefill、decode）对 IO 的贡献只有"什么时候发起"和"发起多少"，不贡献请求本身的特征。所以计算可以被旁路，但**发起 IO 的那条代码路径必须保持原样**：真实的数据加载、真实的 checkpoint 写入、真实的 kvcache 分配与搬运、真实的通信原语调用。

旁路了哪些、保留了什么、带来了什么偏差，逐项登记在配方的「保真边界表」里。没有登记表的配方视为未完成。

### 2. 小规模要能对齐，大规模要能外推

小规模上跑出来的 IO pattern，必须能和同等规模的真实运行对上，否则后面的外推没有依据。大规模结论必须由逐级验证得到，不允许从小规模直接跳到十万卡给结论。

外推的依据是**scaling 不变量**：一组在放大过程中应保持稳定的 IO 特征。不变量选得对不对，决定了外推结论是否可信。

### 3. 结果只回链，不入库

仓库里永远只有：配方、指标、阈值、校验脚本、模板，以及指向外部产物的 URI、sha256、状态。任何一次运行的大报告、trace、日志、产物，都放在对象存储或 CI artifact 里。

判断标准：删掉外部存储里的所有产物，本仓库应当仍然完整、仍然能重新跑出结论。如果删不掉，说明仓库里混进了不该放的东西。

## 成功判据

一个评估集算建成了，需要同时满足：

1. 配方能被另一个人照着跑通，不需要口口相传的隐含步骤。
2. 小规模结果与真实运行在声明的容差内对齐。
3. scaling 不变量在每一级都验证过，且偏差有归因。
4. 覆盖度矩阵上有明确的空白格子，且空白格子被登记为待补，而不是被忽略。
5. 至少一个真实缺口是由评估服务发现、并驱动 playbook 生成新版本补上的（这条衡量的是闭环是否真的转起来了）。

## 角色

| 角色 | 负责 |
|---|---|
| 配方维护者 | 单个评估集的正确性与可复现性 |
| 指标维护者 | `metrics/` 的口径一致，历史结果可比 |
| 服务维护者 | 评估服务的调度、结果存储、回链完整性 |
| 评审者 | 口径可实现、阈值有依据、结论可外推 |

角色可以由同一人兼任，但**改口径的人不能是自己评审自己**。
